# E-Anudaan NGO — parity audit against the live dev portal

**Audited:** 2026-08-22 · **Live:** `https://eanudaan-user-dev.mosje.in`
**Clone:** `apps/hub/src/app/portals/e-anudaan/(ngo)/**`
**Method:** a human-authenticated session was driven for capture; each of the four application
wizards was filled with **dummy data** and walked to its final step; and — at the product
owner's explicit instruction — one SHRESHTA_M2 application was **submitted on the live dev
portal** so the success screen and every post-submit state could be observed rather than
guessed. Raw capture: `CAPTURE-2026-08-22.md`.

> **PII.** The live demo account belongs to a real registered NGO. No name, DARPAN ID,
> registration number, address, bank account, email or mobile from it appears in this repo.
> The clone seeds fictional organisations throughout.

## What "parity" means here

The clone is a SAMAVESH **redesign**, not a pixel copy — that is the estate's standing rule
(`CLAUDE.md`: everything renders from the shared design system). So parity is assessed as
**content, field and state parity**: every route, section, field, option, helper string, empty
state, error state and interaction the live portal has must exist in ours, rendered through the
design system. Visual divergence is intended; missing capability is not.

## Headline finding — there is no shared wizard

The clone ran ONE AVYAY-shaped 8-step wizard for all four schemes. The live portal runs four
different forms:

| Scheme | Steps | Documents | Notes |
|---|---|---|---|
| SHRESHTA_M2 | 6 | 20 (PDF / JPG / PNG) | 3 conditional on ongoing GIA, 1 on a rented building |
| AVYAY | 7 | 9 (PDF) | cost-norms entitlement panel + the 18-head breakdown |
| SMILE | 6 | 20 (PDF) | conditional Website URL and 80G/FCRA detail fields |
| NAPDDR | 3 | 17 (PDF) | the short generic form, at `/apply-grant/step-1` |

Routing also differs from the earlier note: early steps sit on `.../step-1`, the upload step on
`.../step-2`, the read-back on `.../review`.

## Live defects deliberately NOT cloned

1. **"Read-only" fields are editable.** Several wizard fields carry "Read-only — sourced from
   NGO-Darpan / your login" but are not `readOnly` in the DOM. The clone honours the claim.
2. **`110 active beneficiarys` / `Deactivated beneficiarys (14)`** — the live plural is
   misspelled. The clone reads "beneficiaries".
3. **Sidebar active state.** On the live dashboard the sidebar marked *Weekly Attendance*
   `aria-current="page"` while the URL was `/ngo/dashboard`.
4. **Documents Checklist counter reads `20 / 19 uploaded`** on SHRESHTA — more uploaded than
   the denominator. The clone counts mandatory slots.

## Submit chain — captured by submitting (2026-08-22 20:49)

A SHRESHTA_M2 draft was submitted on the live dev portal. This closed the last big unknown.

- **Success screen** captured verbatim — heading, lead, the reference panel with its copy
  control, ROUTED TO / ESTIMATED TIMELINE, the three "What Happens Next?" items, both actions.
- **Reference format corrected.** The location segment is the institution's **address**, not its
  district: uppercased, non-alphanumerics collapsed to `_`, cut to 30 chars. Live produced
  `GIA/2026-27/SHRESHTA_M2/0531_TENEMENT_PARIKSHITLAL_HOS/83515`. The clone now mints references
  with the same algorithm and reproduces that slug exactly.
- **Everything that moves on submit** was recorded: register 71 → 72, bell 3 → 4, a new
  "Application submitted" notice, dashboard total 71 → 72, In Review 21 → 22, donut Submitted
  4 → 5 with all percentages recomputed.
- **The fresh application's detail page** shows a single timeline entry and no attention callout.

The clone's wizard now creates the application for real, so the same chain fires there: verified
72 rows, new top row, new unread notification, dashboard totals moved. As a consequence the
dashboard no longer prints any fixed figure — KPIs, deltas, donut, money, approval rate,
per-scheme cards and the action banner all derive from the store.

## SMILE upload + submit — captured (2026-08-22 21:45)

Twelve labelled placeholder PDFs were uploaded to the live SMILE draft and the application was
submitted. Findings:

- The upload gate holds `Next` disabled until every mandatory slot is filled **and** verification
  settles; then the SHRESHTA test-mode bypass appears and lets you through.
- The AI check is genuinely good: it identified every placeholder, named the document it had
  expected instead, and extracted the fictional organisation name out of the PDF body.
- The review step's Documents markers flip `○` → `✓` once uploaded.
- **The reference number's location segment is per scheme** — SHRESHTA uses the institution's
  address, SMILE uses the site's district + state. The clone now mirrors both, and reproduces
  `GIA/2026-27/SMILE/PUNE_MAHARASHTRA/…` exactly.
- Post-submit the register went 72 → 73 and the scheme filter gained a third option, confirming
  that list is derived from the applicant's own applications.

## Also fixed in passing (pre-existing, blocking)

- Four design-system CSS files used `@apply` in stylesheets imported from their own `.tsx`.
  Tailwind processes those as separate roots, so the **dev server would not boot**. Rewritten as
  token-only plain CSS, which also removed hardcoded `#0373DF` / `bg-white` against the token rule.
- Three generated docs playgrounds had escaped backticks, a `ghost` Button variant and a
  Radix-style Checkbox prop that do not exist — all failing typecheck.
- 34 unescaped JSX entities across six docs pages were failing `npm run lint`.
