# E-Anudaan NGO — parity audit against the live dev portal

**Audited:** 2026-08-22 · **Live:** `https://eanudaan-user-dev.mosje.in`
**Clone:** `apps/hub/src/app/portals/e-anudaan/(ngo)/**`
**Method:** a human-authenticated session was driven for capture; each of the four application
wizards was filled with **dummy data** and walked to its final step; and — at the product
owner's explicit instruction — one SHRESHTA_M2 application was **submitted on the live dev
portal** so the success screen and every post-submit state could be observed rather than
guessed. Raw capture: `CAPTURE-2026-08-22.md`.

> **PII.** The live demo account belongs to a real registered NGO. No name, DARPAN ID,
> registration number, address, bank account, email or mobile from it appears in this repo.
> The clone seeds fictional organisations throughout.

## What "parity" means here

The clone is a SAMAVESH **redesign**, not a pixel copy — that is the estate's standing rule
(`CLAUDE.md`: everything renders from the shared design system). So parity is assessed as
**content, field and state parity**: every route, section, field, option, helper string, empty
state, error state and interaction the live portal has must exist in ours, rendered through the
design system. Visual divergence is intended; missing capability is not.

# Addendum — 2026-08-23 (later): both remaining gaps closed

Neither gap was an automation limit. Both are live defects, and both were proven rather than
assumed.

## 1 · NAPDDR step 2 rejects all seventeen of its own documents

The earlier pass could not tell whether NAPDDR's inert uploader was a live bug or an artefact of
synthetic events. It is a live bug, established by **trusted CDP-level uploads of a real PDF**
(Chrome's own file-input path — indistinguishable to the page from a user picking a file):

| Uploaded to | Live response |
|---|---|
| Document 1 — Memorandum of Association | `Document type 1 is not part of this scheme's document checklist.` |
| Document 7 — Bank Account Details | `Document type 7 is not part of this scheme's document checklist.` |
| Document 17 — Audited Accounts — Previous Year | `Document type 17 is not part of this scheme's document checklist.` |

In every case: **no network request**, counter frozen at `0 / 17 uploaded`, Next permanently
disabled. On a clean load no errors are shown — each one appears only in response to a file being
offered, which proves the handler runs and then refuses the document type.

So NAPDDR's own checklist rejects every entry on it. **No user can complete a NAPDDR application
on the live portal**, and its review step is therefore not a reachable view for anyone — it is
not merely a view this audit failed to reach. Our clone implements the step as specified, which
is the correct behaviour to clone; reproducing the defect would be reproducing a bug.

## 2 · AVYAY's missing Bank Account control, explained

`/ngo/bank-accounts` — reached from the portal's own sidebar — carries two tables:

- **My Bank Accounts**, whose lead reads *"Accounts you save here can be selected when applying.
  Each project must use a separate account."* One account is saved on the demo NGO.
- **Project bank accounts**, whose lead reads *"Each project is paid into its own account… Changing
  one needs the Ministry's approval — it is not something a renewal application can do on its
  own."* Every project row reads **`Not recorded`**, offering only `Request change`.

That is the whole of the AVYAY step-4 dead end. The step requires a Bank Account; the applicant
has a saved account that the page promises is selectable when applying; the application form
renders no control to select it; and the only route to recording one is a change request needing
Ministry approval. The live page's own copy contradicts the live form's behaviour.

**AVYAY steps 5–7 are therefore unreachable for this account by any sequence of inputs**, and no
further attempt will change that. Unblocking needs one of: a fix to the live form so a saved
account is selectable, an approved change request recording a project bank account, or an account
whose projects already have one. Our clone renders a working select — the behaviour the live
page's own instructions describe.

## Route coverage

All ten NGO routes in the live sidebar exist in the clone: `dashboard`, `my-applications`,
`my-applications/deficiencies`, `apply-grant`, `project-location-change`, `bank-accounts`,
`notifications`, `attendance`, `attendance-master`, `cctv`. `/ngo/bank-accounts` carries both of
live's tables, the add/edit/delete flow, and the Ministry change-request path.

# Addendum — 2026-08-23 (final): AVYAY walked to Review, and what our own build was hiding

## The dead end was a wrong turn, not a wall

AVYAY was reported unreachable past step 4. That was wrong, in two ways worth recording because
both are traps this audit will meet again.

**First, the branch.** Every earlier attempt took *Ongoing / Renewal*. Taking **New project**
gives a different and longer wizard — **8 steps, not 7** — and it walks cleanly to Review.

**Second, the "missing" control.** The Bank Account field was never missing. On the NEW branch it
sits on step 5 as a `<select>` labelled *"Select a bank account…"*, listing exactly the account
that `/ngo/bank-accounts` promises will be "selected when applying". It carries **no `id` and no
`name`**, so an id-keyed extractor cannot see it and the label's `for=` binds to nothing. Same
defect class as NAPDDR's anonymous inputs — *not* an absent field. **A field that a name-based
diff reports as missing should be checked for anonymity before it is called a dead end.**

Choosing the account auto-fills Account Number, IFSC and Bank & Branch, which live marks
"Filled in automatically from the Bank Account you select above."

## Live's AVYAY NEW branch, walked end to end

| Live step | Live | Dev | Verdict |
|---|---|---|---|
| 1 · Application Type | 4 | 4 | Match |
| 2 · Organisation Details | 13 | 13 | Match |
| 3 · Project Details | 5 | 5 | Match |
| 4 · **Justification** | 3 | 3 | **Was missing from our clone entirely** — added |

Blockers live never names, for the next walk: step 4 rejects a non-numeric distance, step 5 needs

gates on all 11 uploads.

## Four gaps this walk closed

1. **The Justification step did not exist in our clone.** Three fields, between Project Details
   and the infrastructure step.
2. **Documents are branch-dependent.** A new project is asked for the NGO's PAN, two years of
   annual reports, two years of audited accounts and a fire safety audit (11); a renewal for a
   budget estimate, the project's audited accounts and a GFR-12A (9). `DocDef` now takes a
   `showWhen`, and the union is ordered so each branch filters back to live's own sequence.
3. **Cost norms are computed per capacity, not fixed.** Our table was the 50-beneficiary one, so a
   25-beneficiary home was shown figures up to double what it may draw — and not by one ratio: a
   Superintendent is one post either way, food doubles, MTS goes 3 → 4. Both columns are now
   carried and chosen by project type.
4. **The panel showed norms where live shows the central share**, which made the Total wrong too —
   live totals the two *shares*, not the two norms. Ours now reproduces live exactly:
   recurring norm ₹24,38,356 less ₹1,78,200 owned-building deduction → ₹20,34,140; non-recurring
   ₹3,09,105 → ₹2,78,195; **Total ₹23,12,335**; attendance-linked ₹9,91,216. All 18 rows match
   head for head, including the central-share column.

## Three faults only walking OUR build could find

A schema diff compares declarations. These were live-behaviour gaps that matched on paper:

- **The three bank fields were required, read-only, and never filled.** Choosing an account left
  the step blocked on boxes the applicant cannot type into — the same shape as the SHRESHTA totals
  bug. `applyAutoFields` now derives them.
- **`cityCategory` was declared as an auto rule months ago and never implemented.** One required
  read-only field away from the identical dead end. Now implemented.
- **The checklist's `showWhen` used `"NEW"`/`"ONGOING"`,** which this form never holds — the values
  are `"New project"` and `"Ongoing / Renewal of an existing project"`. Every conditional document
  would have stayed hidden on both branches. **A conditional is not verified until it is walked.**

## And one the visual audit found

The eighth step broke the stepper. `.ds-stepper__text` sizes to its content inside a centred flex
column, so at ~800px "Infrastructure," spilled 8px into "Justification" and the two read as one
word. Constraining it made the labels break mid-word instead ("Organisatio n Details"), so above
640px an eight-step stepper now shows only the current label — the treatment the ≤640px rule
already uses, with the rest kept in the DOM for assistive technology. All eight show at 1280px
with no overlap. Stylelint clean, no raw values.

## Deliberate divergences, restated

- Our fields carry `id`/`name`; live's bank select, its ten SMILE undertakings and all seven
  NAPDDR inputs do not.
- `fld_key_staff_1` validates instead of silently stripping digits.
- Live disables Submit until the declaration is ticked; ours keeps it focusable and explains the
  gate in the same sentence live uses. Both refuse the submission.
- The cost-norms lead names the project type it computed for; live leaves it implicit.

## What remains unverified, and why

**NAPDDR's review step**, still — its document checklist rejects all 17 of its own entries, so no
user reaches it. Our implementation of that view is exercised and rendering; it is live that
cannot be compared against.
